# One-message publication workflow — Blog RU/EN and Cases RU/EN

**Owner's intended UX:** The Owner prepares an image, uploads it into the connected version-control repository or gives its exact accessible asset path, then sends the final text to the relevant Codex chat with **«ПУБЛИКУЙ» / «PUBLISH»**. The agent performs all technical work without asking the Owner to understand Git, Astro, schemas, routing or SEO metadata. **This explicit message is approval to publish the supplied text and specified image, not permission to rewrite them.**

Use this format in any of the four dedicated chats:

```text
ПУБЛИКУЙ НА IVANDUBAI.XYZ

Раздел: <Blog RU | Blog EN | Cases RU | Cases EN>
Изображение: <точное имя файла или путь в репозитории; внешний URL — только по отдельному указанию Owner>
Текст:
<полный окончательный текст с заголовком>
```

The chat role fixes both section and language (Blog RU / Blog EN / Cases RU / Cases EN); the `Раздел:` line is an explicit consistency check, not a role override. If omitted, use the fixed chat role without asking. STOP before creating files and ask one precise question if the named section differs from the role; the dominant narrative language of the supplied body differs from the role language (ordinary English names/terms inside Russian prose are not a mismatch); or the message asks to publish two sections or languages in one task. Never re-route, switch roles or publish a translation automatically. For the second language the Owner sends the approved text to its own chat.

## Agent must do autonomously — no repeated setup instructions to Owner

1. **Find the correct checkout.** Inspect `git rev-parse --show-toplevel` and `git remote -v`. If the Codex workspace is an unrelated, empty repo such as `codex/add-project-config`, do NOT use it to publish. Find the existing `Ivtekb/ivandubai-astro` checkout; if absent and GitHub access permits, clone `https://github.com/Ivtekb/ivandubai-astro.git` to a new isolated folder (never overwrite existing files). Perform all publication commands in that real checkout. If neither is possible, stop with **one short technical blocker** rather than asking the Owner to create the checkout manually or claiming readiness.
2. **Internal preflight** on every task: fetch fresh `origin/main`; read root `AGENTS.md`, `src/content/AGENTS.md`, `docs/CODEX_CONTENT_OPERATIONS.md`, `docs/SEO_AI_PUBLICATION_CHECKLIST.md`, latest Owner Policy, current content schema, actual route and BaseHead templates, and recent relevant examples. Do not dump the preflight to Owner unless a blocker exists. Retain main SHA and test evidence in the PR/release log.
3. **Image:** use the exact Owner-specified image from the repository, served from `public/` (e.g. `public/post-27.jpg`). Verify filename case, bytes, supported format, dimensions and resulting path in `seo.image.src`. If Owner uploaded the file elsewhere in the repository, copy those exact bytes into an appropriate `public/` path on the publication branch; never crop, regenerate, replace or modify the image. Do not hotlink an outside URL by default: external images are permitted only when Owner **explicitly** directs external hosting and that URL is verified accessible. If absent or ambiguous, ask one precise question.
4. **Preserve final body exactly**: do not remove, rephrase, translate, add facts, inject editorial CTAs or change author voice. If Markdown is needed for the Astro renderer, only make clearly mechanical formatting transformations (headings, whitespace, bullet syntax), preserving every word and paragraph order. A standalone user-supplied title becomes the template-generated H1; body Markdown begins at H2, avoiding a duplicate H1. Any substantive copy change must be approved by Owner before proceeding.
5. **Generate technical packaging automatically** from the exact Owner text: unique filename ID and URL, current date in `Asia/Dubai` as `publishDate` only if the Owner didn't specify another date; serialize the chosen date exclusively as ISO `YYYY-MM-DD` (never a free-form date such as `Jan 15 2024`); correct schema-required frontmatter; concise description/excerpt and SEO title without new factual claims (SEO description ≤150 characters); approved image path/alt that literally describes the image; tags from the real topic without invented classifications. These derived non-body fields are approved by the Owner's explicit **PUBLISH** command *only insofar as they faithfully summarize supplied material*. If a title, image, dated claim or compliance requirement cannot be resolved faithfully, stop and ask a **single precise question**, never fabricate it.
6. **Reuse current site architecture**: no hard-coded canonical or hreflang frontmatter as authoritative; BaseHead controls Article+Person JSON-LD, OG, canonical and localized language alternates. If different RU/EN slugs require a new `explicitTranslationPairs` entry, get Claude technical review first. Do not add duplicate schema, fake sources, fabricated permit numbers or auto-edit existing publications. Apply all mandatory new-page SEO/AI checks.
7. **Build, review and publish** on a dedicated branch/PR (never push directly to `main`): clean `TZ=UTC npm run build` of current main vs branch and expected file-by-file output diff, validate image, route, canonical/hreflang, Article/Person, heading hierarchy, listing, RSS/sitemap, navigation, analytics and Formspree. For a **content-only** PUBLISH adding approved Markdown and the exact selected image, no extra pre-merge Claude gate is required: after the checks Codex can merge/deploy under Owner's explicit PUBLISH authorization and must personally verify live production, then record outcome. Follow the independent post-release review convention in Owner Protocol #16 (batching only if explicitly allowed); do not claim that review passed until Claude actually supplies a verdict. If publication also changes technical source code (e.g. `BaseHead.astro` translation map), obtain Claude's independent technical agreement before implementing/merging as the protocol requires. Do not seek Claude editorial approval. When an action is unavailable, report the exact blocker and minimal next action.
8. **Return only the result Owner needs:** public RU/EN page link, whether deployed, image confirmation and short test status. Do not flood the Owner with Git SHA, long checklists, or a new request to approve the supplied text; technical evidence belongs in the PR/issue.

## Documentation-build guard

Astro/Tailwind v4 can scan Markdown in `docs/` and `AGENTS.md`; documentation-only PRs can therefore unexpectedly alter generated CSS. For ANY documentation change, compare a clean `TZ=UTC npm run build` of current main and the proposed patch and HOLD on any unapproved output difference. Do not infer that documentation edits are output-neutral.

## Explicit boundaries

- **ROLE/SECTION/LANGUAGE gate:** the chat's selected role is authoritative. If `Раздел:` names a different Blog/Case or RU/EN role, if the supplied content's dominant language differs from the selected role, or if one request asks for both languages or sections, STOP before file creation and ask one precise clarification. Do not silently translate, redirect, split or change roles. An omitted `Раздел:` inherits the chat's role.
- **DRAFT / «Подготовь черновик»** means prepare a draft, do not publish.
- **PUBLISH / «Публикуй» + final copy + specified image** means the Owner approved that exact material for publication and its *faithful technical metadata*. It does not authorize stylistic editing, invented claims, publication of other language versions or changes to existing pages.
- If the user simply pastes material without PUBLISH, ask whether the request is to draft or publish; do not assume.
- If a previous publication exists at the target ID, STOP (never overwrite). Preserve all Owner-approved existing publications.
- Keep user-facing interaction minimal; all reproducible checks and source-of-truth comparisons occur autonomously.
