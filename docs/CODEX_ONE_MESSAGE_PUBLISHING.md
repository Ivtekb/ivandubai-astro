# One-message publication workflow — Blog RU/EN and Cases RU/EN

**Owner's intended UX:** The Owner prepares an image, uploads it into the connected version-control repository or gives its exact accessible asset path, then sends the final text to the relevant Codex chat with **«ПУБЛИКУЙ» / «PUBLISH»**. The agent performs all technical work without asking the Owner to understand Git, Astro, schemas, routing or SEO metadata. **This explicit message is approval to publish the supplied text and specified image, not permission to rewrite them.**

Use this format in any of the four dedicated chats:

```text
ПУБЛИКУЙ
Картинка: 28
Текст:
<готовый полный текст нужного языка, включая заголовок>
```

The Owner may alternatively supply `Изображение: /post-28.jpg` or the exact repository file path. The image number is a convenient asset locator only; it is not permission to change the article ID or assume an unrelated bilingual counterpart. `Раздел:` is optional because each chat has a fixed role; if supplied, it must match that role.

**No writing, translating or redrafting in a PUBLISH workflow.** Another editorial chat produces the ready, Owner-approved RU or EN text. Codex receives it and publishes it *as supplied*; it never initiates a translation stage, provides editorial options or asks for an additional translation approval after PUBLISH. The chat role fixes both section and language (Blog RU / Blog EN / Cases RU / Cases EN); the `Раздел:` line is an explicit consistency check, not a role override. If omitted, use the fixed chat role without asking. STOP before creating files and ask one precise question if the named section differs from the role; the dominant narrative language of the supplied body differs from the role language (ordinary English names/terms inside Russian prose are not a mismatch); or the message asks to publish two sections or languages in one task. Never re-route, switch roles or publish a translation automatically. For the second language the Owner sends the approved text to its own chat.

## Agent must do autonomously — no repeated setup instructions to Owner

1. **Find the correct checkout.** Inspect `git rev-parse --show-toplevel` and `git remote -v`. If the Codex workspace is an unrelated, empty repo such as `codex/add-project-config`, do NOT use it to publish. Find the existing `Ivtekb/ivandubai-astro` checkout; if absent and GitHub access permits, clone `https://github.com/Ivtekb/ivandubai-astro.git` to a new isolated folder (never overwrite existing files). Perform all publication commands in that real checkout. If neither is possible, stop with **one short technical blocker** rather than asking the Owner to create the checkout manually or claiming readiness.
2. **Internal preflight and asset gate — FIRST:** verify the selected role, exact final text, and image path **before** running npm/build/preview or spending time on the article. Search the current checkout and accessible Git repository/refs **once** for the named image; a file already uploaded to VCS may not yet be present in the local checkout. Refresh needed refs safely without overwriting changes. If missing/ambiguous, ask one precise question immediately and stop only this publication; never repeatedly poll another PR, image or permissions. Then fetch fresh `origin/main`; read root `AGENTS.md`, scoped instructions, this runbook, the SEO/AI checklist, Owner Policy when accessible, schema/routes/BaseHead and a relevant example. Retain SHA and test evidence in PR/release log; routine preflight stays internal.
3. **Image number resolution — FIRST:** `Картинка: 28` means find the actual unique `public/post-28.jpg` (or exactly one `post-28` asset with an approved image extension; for Cases a unique matching `case-28` file may be used). Check known local checkout and reachable version-control files; do not fabricate a file or silently choose between multiple matches. If none or ambiguous, ask one precise question; otherwise do not ask the Owner to restate a full file path. A supplied absolute file path or URL can be used only under the existing repository/explicit-external-host rules. **The number is NEVER an instruction to use a numbered URL.** For a new original publication, derive a descriptive route ID from the approved topic/title, such as `dubai-branded-residences` → `/blog/dubai-branded-residences/` or `/en/blog/dubai-branded-residences/`. Use the SAME semantic slug for a newly paired RU and EN article to obtain current Astro's automatic hreflang without modifying BaseHead. If EN is an approved adaptation of an already published *legacy* numeric RU `post-28`, preserve `src/content/blog/en/post-28.md` to keep the existing live pair; do not silently rename already published URLs.
4. **Image — two separate outputs are required:** use the exact Owner-specified image from the repository, served from `public/` (e.g. `public/post-27.jpg`). The image must (a) populate `seo.image.src`/approved localized alt for OG/Article and (b) appear visibly as a Markdown image in the article/case **body**, immediately after the heading/date rendered by the Astro template and before the opening paragraph. Current RU/EN Blog/Case route components render `<Content />` but **do not insert a hero image from frontmatter**, so metadata-only is a release-blocking defect. For each NEW page with a supplied image, run the dependency-free built-HTML check `node scripts/verify-publication-hero.mjs --route /blog/<id>/ --image /post-27.jpg` (substitute exact `/en/blog/`, `/cases/` or `/en/cases/` route). It must find a nonempty localized alt inside `<article>` and matching OG/JSON-LD image; no separate H1 in Markdown. Verify filename case, bytes, supported format, dimensions and resulting path in `seo.image.src`. If Owner uploaded the file elsewhere in the repository, copy those exact bytes into an appropriate `public/` path on the publication branch; never crop, regenerate, replace or modify the image. Do not hotlink an outside URL by default: external images are permitted only when Owner **explicitly** directs external hosting and that URL is verified accessible. If absent or ambiguous, ask one precise question immediately, before lengthy preparation. If the image exists in a newly committed remote ref but is absent locally, retrieve it safely rather than requesting the Owner to upload it again.
5. **Preserve final body exactly**: do not remove, rephrase, translate, add facts, inject editorial CTAs or change author voice. If Markdown is needed for the Astro renderer, only make clearly mechanical formatting transformations (headings, whitespace, bullet syntax), preserving every word and paragraph order. A standalone user-supplied title becomes the template-generated H1; body Markdown begins at H2, avoiding a duplicate H1. Any substantive copy change must be approved by Owner before proceeding.
6. **Generate technical packaging automatically** from the exact Owner text: unique **descriptive public URL slug as the filename ID** (short, meaningful, lower-case words separated with hyphens, reflecting actual title/search intent; never `post-N`, `case-N` or the image number for a new original page), current date in `Asia/Dubai` as `publishDate` only if the Owner didn't specify another date; serialize the chosen date exclusively as ISO `YYYY-MM-DD` (never a free-form date such as `Jan 15 2024`); correct schema-required frontmatter; concise description/excerpt and SEO title without new factual claims (SEO description ≤150 characters); approved image path/alt that literally describes the image; tags from the real topic without invented classifications. These derived non-body fields are approved by the Owner's explicit **PUBLISH** command *only insofar as they faithfully summarize supplied material*. If a title, image, dated claim or compliance requirement cannot be resolved faithfully, stop and ask a **single precise question**, never fabricate it.
7. **Reuse current site architecture**: no hard-coded canonical or hreflang frontmatter as authoritative; BaseHead controls Article+Person JSON-LD, OG, canonical and localized language alternates. If different RU/EN slugs require a new `explicitTranslationPairs` entry, get Claude technical review first. Do not add duplicate schema, fake sources, fabricated permit numbers or auto-edit existing publications. Apply all mandatory new-page SEO/AI checks.
8. **One-command technical release:** after Codex packages the exact final text and already-selected image into a NEW Markdown page, invoke `node scripts/publish-release.mjs --approved-publish --route <actual-route> --image <number>` from a clean publication branch. `--dry-run` is available for no-network preflight. The driver handles exact Git scope, PR, GitHub Actions `Publish Quality Gate` (two clean UTC builds, output diff, SEO/Article/Person/canonical/hreflang/visible hero/RSS/sitemap), Vercel preview, controlled merge, and read-only full-production byte parity. This replaces manual npm, browser and repeated build loops for content-only Markdown pages on unchanged Astro templates. If shell networking or `gh` is blocked by sandbox, Codex uses connected GitHub tools for the same steps without repeated network retries or new Owner authorization. If technical Astro/code changes are needed, STOP and obtain independent Claude technical review before merge. See `docs/CODEX_AUTOMATED_PUBLISHING.md`.

9. **Return only the result Owner needs:** public RU/EN page link, whether deployed, image confirmation and short test status. Do not flood the Owner with Git SHA, long checklists, or a new request to approve the supplied text; technical evidence belongs in the PR/issue.

## Prepared environment and test efficiency

- **Dependency permission:** `npm ci` is an already-approved routine publishing step in the isolated, correct checkout. Install dependencies using the lockfile automatically when missing or invalid; do not wait for another editorial approval. Respect any actual sandbox/OS/network permission prompt; request that permission once, never bypass or repeatedly retry without a change.
- **Reproducible builds:** keep baseline and publication build caches / Astro-Vite output isolated per worktree; never symlink mutable `.astro`, `dist` or Vite cache between worktrees. Reuse a verified dependency installation with an unchanged lockfile when safe; otherwise `npm ci`. One clean UTC baseline build and one clean UTC candidate build with exact output-diff are mandatory under Owner Policy. Cache a completed baseline by exact main SHA + lockfile + environment hash only when its complete evidence is preserved and verifiable. If build/test content and main SHA haven't changed, do not rerun the entire suite as a ritual.
- **Preview tool fallback:** try the regular visual browser once; if the remote CUA browser is broken, switch directly to Chrome/headless with explicitly checked CSS viewport and screenshot dimensions (e.g. 390px mobile) instead of lengthy CUA debugging. HTTP, canonical, structured data, RSS, sitemap and tracking are verifiable without a screenshot. Do not mislabel an untested visual check as passed.
- **Release order, not PR count:** independent Blog/Case content PRs and backlog draft PRs can coexist. Just before MERGE/production, refresh main, ensure no overlapping deployment and repeat affected build checks if the base advanced. Never poll a parked PR or require its closure. Keep technical-code Claude pre-merge review; content-only PUBLISH uses Codex QA plus independent post-release protocol.
- **Execution record:** log image availability at start, dependency/build reuse, number of actual build attempts, successful built-HTML hero validator, PR created/merged, production ready, live URL and on-page image/asset checks. Metadata-only images must be reported FAIL. Track where time is spent to spot recurring infrastructure failures; do not present an aspirational runtime as a guarantee.

## Documentation-build guard

Tailwind v4 can scan docs/ and `AGENTS.md` Markdown files during Astro build; documentation-only PRs can therefore unexpectedly alter generated CSS. For ANY documentation change, compare a clean `TZ=UTC npm run build` of current main and the proposed patch and HOLD on any unapproved output difference. Do not infer that documentation edits are output-neutral.

## Explicit boundaries

- **ROLE/SECTION/LANGUAGE gate:** the chat's selected role is authoritative. If `Раздел:` names a different Blog/Case or RU/EN role, if the supplied content's dominant language differs from the selected role, or if one request asks for both languages or sections, STOP before file creation and ask one precise clarification. Do not silently translate, redirect, split or change roles. An omitted `Раздел:` inherits the chat's role.
- **DRAFT / «Подготовь черновик»** means prepare a draft, do not publish.
- **PUBLISH / «Публикуй» + final copy + specified image** means the Owner approved that exact material for publication and its *faithful technical metadata*. It does not authorize stylistic editing, invented claims, publication of other language versions or changes to existing pages.
- If the user simply pastes material without PUBLISH, ask whether the request is to draft or publish; do not assume.
- If a previous publication exists at the target ID, STOP (never overwrite). Preserve all Owner-approved existing publications.
- Keep user-facing interaction minimal; all reproducible checks and source-of-truth comparisons occur autonomously.
